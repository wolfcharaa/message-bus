# Миграция с v5.0 на v5.1

v5.1 - minor release MessageBus. Основное изменение: PostgreSQL runtime получает schema foundation для устойчивого worker control-plane, schema version validation и публичный technical status `interrupted` для queue jobs.

## Что меняется

- Добавлена служебная таблица `message_bus__schema_versions`.
- Queue schema получила публичный status `interrupted`.
- Queue schema получила index для `interrupted` jobs.
- Worker control-plane переходит на явные таблицы `message_bus__worker_control_*`.
- Добавлены normalized foundation tables для command deliveries, acknowledgements и audit.
- Добавлена таблица desired state `message_bus__worker_desired_state`.
- Добавлена команда проверки schema `message-bus:postgres:schema:validate`.
- `worker:run --mode=auto --transport=postgres` теперь делает fail-fast schema validation до старта обработки jobs, если runtime предоставляет PostgreSQL schema validator.

## Новые таблицы

v5.1 использует следующие PostgreSQL таблицы:

- `message_bus__queue_jobs`;
- `message_bus__schema_versions`;
- `message_bus__worker_control_commands`;
- `message_bus__worker_control_command_deliveries`;
- `message_bus__worker_control_command_acknowledgements`;
- `message_bus__worker_control_command_audit`;
- `message_bus__worker_desired_state`;
- `message_bus__worker_instances`;
- `message_bus__worker_child_instances`.

## Безопасный порядок обновления

1. Остановить producers, которые создают новые async jobs, если deploy меняет message bindings или runtime bootstrap.
2. Выполнить `drain` для active workers или остановить workers штатным способом.
3. Применить SQL schema v5.1 через migration tool приложения.
4. Запустить schema validation command.
5. Обновить application runtime/bootstrap, если он вручную регистрирует worker control storage/table definitions.
6. Запустить workers.
7. Проверить `worker:status` и логи workers.

## SQL source of truth

SQL templates лежат в библиотеке:

```text
resources/postgres/schema/5.1/queue.sql
resources/postgres/schema/5.1/worker-control.sql
resources/postgres/schema/5.1/all.sql
```

Для приложения рекомендуется брать эти файлы как source of truth и применять их через свой migration tool.

Пример ручной проверки SQL:

```bash
psql "$DATABASE_URL" -f vendor/romanfedorskij/message-bus/resources/postgres/schema/5.1/all.sql
```

Если вы не хотите хранить SQL file в миграции приложения, можно сгенерировать актуальный SQL командой:

```bash
vendor/bin/message-bus schema:postgres --with=all
```

## Проверка schema

После применения SQL выполните:

```bash
vendor/bin/message-bus message-bus:postgres:schema:validate \
  --dsn='pgsql:host=127.0.0.1;port=5432;dbname=app' \
  --user='app' \
  --password='secret'
```

Команда ничего не меняет в БД. Она проверяет:

- наличие `message_bus__schema_versions`;
- версии components `queue` и `worker_control`;
- наличие ключевых таблиц;
- наличие критичных колонок;
- наличие critical indexes/unique constraints.

Успешный результат:

```text
component=queue required=5.1 current=5.1
component=worker_control required=5.1 current=5.1
PostgreSQL schema is compatible.
```

Если schema устарела или применена частично, команда вернет non-zero exit code:

- `20` - schema version mismatch/missing;
- `21` - structural validation failed.

## Auto worker fail-fast

`worker:run --mode=auto --transport=postgres` больше не должен стартовать на несовместимой PostgreSQL schema.

Если runtime создан через `MessageBusRuntime::postgres()`, validator подключается автоматически.

Если runtime собирается вручную через container, зарегистрируйте:

```php
use Wolfcharaa\MessageBus\Postgres\PostgresSchemaValidatorInterface;

$container->set(
    PostgresSchemaValidatorInterface::class,
    fn () => $postgresSchemaValidator,
);

$container->set('message_bus.postgres_schema_validator', fn () => $postgresSchemaValidator);
```

Достаточно одного из этих service ids.

## Что сделать в приложении

Если приложение использует стандартный `MessageBusRuntime::postgres()`, обычно достаточно:

1. Обновить composer package до `^5.1`.
2. Применить SQL из `resources/postgres/schema/5.1/all.sql`.
3. Запустить `message-bus:postgres:schema:validate`.
4. Перезапустить workers.

Если приложение вручную создает `WorkerControlTableDefinition`, обновите имена таблиц или явно зафиксируйте свои:

```php
use Wolfcharaa\MessageBus\Worker\WorkerControlTableDefinition;

$definition = new WorkerControlTableDefinition(
    commandsTable: 'message_bus__worker_control_commands',
    desiredStatesTable: 'message_bus__worker_desired_state',
    workerInstancesTable: 'message_bus__worker_instances',
    childInstancesTable: 'message_bus__worker_child_instances',
    acknowledgementsTable: 'message_bus__worker_control_command_acknowledgements',
    commandDeliveriesTable: 'message_bus__worker_control_command_deliveries',
    commandAuditTable: 'message_bus__worker_control_command_audit',
    schemaVersionsTable: 'message_bus__schema_versions',
);
```

## Runtime изменения v5.1

После schema foundation v5.1 runtime получил:

- retry/reconnect executor для PostgreSQL transient disconnects;
- reconnect-capable `PdoConnectionProviderInterface` и `CallbackPdoConnectionProvider`;
- явную ошибку для `StaticPdoConnectionProvider::reset()`, потому что готовый `PDO` не умеет reconnect;
- resilient worker-control storage;
- resilient queue storage для read/status и idempotent state transitions;
- запрет automatic retry для `enqueue`, `enqueueMany` и `next`, пока у этих операций нет отдельного deterministic idempotency contract;
- CLI output contract для `worker:run`;
- базовую hybrid failure policy для auto worker loop;
- fork lifecycle hooks `beforeFork`, `afterForkInParent`, `afterForkInChild`.

## Что пока не входит в v5.1

Следующие части остаются отдельными задачами:

- deterministic enqueue id/idempotency key для безопасного retry insert новой job;
- `scale-concurrency` и `reload-config`;
- полноценный recovery API для `interrupted` jobs;
- отдельные UI/API read models поверх control-plane таблиц.
